# Macro mechanism authoring contract

**Scope:** new ScraperX ascent slices on `ChatGPT`. The Atlas owns geometry; `00_START_HERE.md` owns current status. The old AS-001–015 queue is retired, not a prerequisite list.

## Work backward, verify forward

Start with the player's supported destination. Resolve transfer geometry, load transmission, source energy and reachable control in that order. Then exercise the whole physical chain forward through normal input. Backward derivation is a design method, not evidence that a mechanism works.

First state the player problem under GDD §16: what the player can inspect, why the initial arrangement blocks useful ascent, which reachable intervention can change it, and how an ineffective attempt gives useful feedback. Compare the intended decision and traversal with recent encounters. A physical mechanism can be simple; the player’s contribution and useful aftermath must be concrete.

| Contract | Must be stated |
|---|---|
| Receiver | Native support identity, walking surface, clear standing area, stability, onward action and fall recovery |
| Transfer | Contact/capture volume, posture/clearance, relative velocities and allowable placement variation |
| Transmission | Actual bodies, joints, contact/rope paths, arm lengths and their changing mechanical advantage |
| Source | Mass/COM/inertia, usable height or spring work, finite drive, friction/impact/braking losses and remaining energy |
| Player access | Supported approach, visible control, bounded effort, available hands and early/late input consequences |
| Persistence/retry | Spent inventory, lost loads, return path, rearm energy and a coherent checkpoint restore |
| Initial state and control | Body poses/velocities, constraints, contact parameters, stored energy, persistent state and ordered player inputs; no hidden success-driven motion |
| Assembly and limits | Visible support/pivot, dimensions, mass distribution/inertia, motion freedoms, full swept clearance, stops, friction/restitution and permitted travel |
| Player problem and variety | Observable obstruction, meaningful intervention, ineffective attempt, changed traversal, comparison with recent encounters and physically valid alternatives |

Inputs and outputs match at the same instant in position, orientation, velocity, load, available energy, constraint state and player access. Same altitude or same label does not close a handoff. Reject hidden stubs, remote attachment, route completion flags and pose snapping.

## Readability and pace

Use large geometric causes: something rolls, tips, swings, strikes, lands or becomes supported. See the major handoff from the approach or operating position. Exercise an actual first-person pass and a miss and record the gameplay outcome; screenshots are optional diagnostics. UI telemetry is supplementary. Prefer wide capture regions to intricate projectile catches. The normal path must be worth doing even when legal parkour offers an alternative. Do not defend a weak mechanism with invisible barriers.

## Movement and units

SI, Y-up. Distinguish body COM from walking surface and capsule centre. The current standing capsule is 1.8 m tall, radius 0.35 m; crouched height 1.2 m; step-up 0.35 m. Inspect source/runtime for each actual reach, clearance and moving-support transfer. Preserve `v_linear + omega × r` and inherited detach momentum. Do not retune global movement to hide a local geometry flaw.

Verify the actual player body and interaction implementation at the current head. For a dynamic player, weight and landing impulses flow once through physical contact; do not add a second standing-weight force. Include rotating-support point velocity, departure momentum, unloading and any distinct hanging controller in the accounting. A grip that releases after an excessive measured impulse is not automatically a continuously force-limited actuator.

## Evidence and readiness

Classify factual claims as SOURCE, OBSERVED RUNTIME, DESIGN TARGET, HISTORICAL OBSERVATION or UNKNOWN; these describe evidence, not numerical provenance. For compiler quantities additionally use its declared CHOSEN, DEFAULT, MEASURED, DERIVED, INTEGRATED or UNRESOLVED labels. A value read from code remains a source fact; measurement or validation requires the stated observation. Keep lifecycle separate from evidence and READY/BLOCKED. A critical unresolved release load, receiver, stopping law or recovery path blocks a ready implementation contract; guessing a number does not resolve it. Use explicit local prototypes to answer unknowns rather than importing an entire old campaign.

## 8. Mechanical close for a new ticket

Each bounded ticket names objective, existing truth, authority, native state owner, allowed seam, forbidden shortcuts, actual proof path and completion condition. Include the contracts above, one legible normal sequence, physically meaningful negative cases and the player's terminal support. A ticket may span files but should implement one useful causal slice.

Read and run the applicable installed compiler workflow before implementation. Resolve gravity/torque through the full stroke, inertia, force/work limits, contact and impact losses, support reactions, stopping, entry/exit clearance and recovery using ThreeSpine as appropriate. Declare reduced-model assumptions; compare applicable parameter bands and timestep refinement with native behavior. For a player-loaded tipper, exercise unloaded equilibrium, near/far and opposite loading, landing, departure/unloading, mechanical limits and a recovery path. For other assemblies derive equally meaningful falsifiers from their actual load path. Then exercise collision and visible motion together through normal gameplay, retained route regressions and the available delivery path. A dedicated fixture supplements that route; it does not replace it.

Proofs must distinguish normal gameplay from an explicit regression fixture. Verify absence of removed visual AND collision content. A fresh APK proves packaging; install, execution, device readability and sustained performance require device evidence.
