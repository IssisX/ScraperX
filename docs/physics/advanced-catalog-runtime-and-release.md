## I. Preserve world lifetime while evaluating job scheduling

**Classification: Production-established** for RAII and ordered teardown; changing worker count remains an experimental candidate.

1. **Problem/opportunity.** Restart or overlapping instances must not invalidate another world's shapes, constraints or factory. Increasing concurrency can add overhead or races. Existing lifetime protection should be preserved; no teardown defect was reproduced here.
2. **Owner/source.** `Simulation::PhysicsWorld` owns allocator, jobs, physics and machines (`src/sim/simulation.cpp:1831`, `8083`). `JoltRuntimeLease` serializes registration with a mutex/refcount (`1233`); its first-declared member outlives later members. Destruction removes listeners, machines, constraints, then bodies (`2051`); `kit::Kit::~Kit` removes joints before bodies (`src/sim/mechanism_kit.cpp:165`).
3. **Math/assumptions.** Lifetime is a dependency order: every constraint referencing body B must die before B; every world using registered types must die before the last lease. Counts are dimensionless. For scheduling, measured step time is `T = T_serial + T_parallel/p + T_dispatch + T_contention` in milliseconds, where p is effective worker parallelism. This estimates tradeoffs, not speedup guarantees.
4. **Pinned APIs.** `JobSystemThreadPool(uint,uint,int)` exists (`Jolt/Core/JobSystemThreadPool.h:32`); ScraperX passes **1** worker and owns an **8 MiB** `TempAllocatorImpl`. `PhysicsSystem::Update(float,int,TempAllocator*,JobSystem*)` is at `PhysicsSystem.h:162`; `RemoveConstraint` at `131`; `BodyInterface::RemoveBody`/`DestroyBody` at `102`/`89`. The header explicitly requires removal before destruction. `BodyLockRead`/`BodyLockWrite` exist in `BodyLock.h:100`/`106`.
5. **Native approach.** Preserve RAII. If profiling supports concurrency changes, vary only worker count, keep mutation outside `Update`, and retain locking interfaces unless phase guarantees justify no-lock access. Keep global registration out of machine constructors.
6. **Alternatives/tradeoffs.** More workers can shorten solving but increase wakeup, thermal and contention costs. Custom allocators or lock-free queues require a demonstrated bottleneck.
7. **Expected behavior.** Repeated world construction, restart and destruction leave surviving worlds functional. Worker-count experiments preserve the same gameplay acceptance tolerances. These are proposed acceptance outcomes, not new runtime observations.
8. **Failures/edges.** Destroyed bodies still referenced by constraints, callbacks surviving teardown, failed body locks, no-lock access overlapping jobs, or global factory removal while a second world lives. Refcount protection does not make every simulation method safe for arbitrary simultaneous calls.
9. **Instrumentation/cost.** Record construction/destruction duration, body/constraint counts, step p50/p95/p99 and allocator use. Aggregate outside contact hot paths. Device thermal behavior and phone budgets remain unmeasured.
10. **Rejecting test.** Proposed lifetime falsifier: create two worlds, destroy one with carry/grip constraints active, step the survivor, destroy it, then construct/step another. Reject crashes, stale handles or missing support; compare body counts with the expected inventory. Run a sanitizer-capable supported host configuration when available. This specific lifetime campaign was not executed here.

## J. Native event receipts drive landing and machinery feedback

**Classification: Production-established** technique with existing implementation; perceptual tuning requires play/listening evidence.

1. **Problem/opportunity.** Idle riders should not sound like walking; restart should not replay impacts; camera/dust should communicate loads without altering support. Existing source addresses these boundaries.
2. **Owner/source.** Native contact and recovery publish state (`src/sim/simulation.cpp:8054`); bridge dictionaries expose it (`src/bridge/scraperx_simulation.cpp:685`, `552`). `godot/presentation/audio/audio_director.gd:282` consumes support-relative velocity and event counters; `landing_camera_response.gd:28` moves the lens only; `reclaim_dust.gd:89` consumes rubble receipts. `main.gd:864` owns presentation reset after native restart.
3. **Math/units.** Grounded foot velocity is `v_rel = v_player − v_support(point)` in m/s, including `ω × r`. Approach energy is `E_n = ½ m v_n²` in joules under the native reduced player-mass model; closing speed is not an impulse in N·s. The camera solves `x'' + 2ω x' + ω²(x−target)=0`, with ω in s⁻¹, displacement in metres or radians. Its closed-form update assumes a constant target during each render interval.
4. **Pinned APIs.** `BodyInterface::GetPointVelocity` (`BodyInterface.h:212`) and `GetCenterOfMassTransform` (`196`) provide authoritative transport. Read velocities from `GetLinearVelocity`/`GetAngularVelocity` (`207`/`211`). Presentation adds no Jolt contact solver, body or constraint.
5. **Native approach.** Retain native event receipts, support IDs, units and validity flags. Emit at the real owner event, publish after solving, consume once, reset baselines on restart/death. Disabled feedback must leave native state unchanged.
6. **Alternatives/tradeoffs.** World-speed footsteps misread idle riders; render velocity differences confuse teleports with impacts. Synthetic impulses overstate contact evidence. Existing bounded exaggeration offers readable feedback without a second physical authority; full physical camera-body coupling would add unwanted gameplay consequences.
7. **Expected behavior.** Idle riders remain quiet; stronger landings produce stronger bounded lens response; machinery sound follows actual load/motion; restored events remain quiet. Phone feel/listening were not observed here.
8. **Failures/edges.** Counter rewind, death and success cues firing together, multiple events between rendered frames, missing/non-finite values, remote impacts, reduced-motion toggles and pool exhaustion. A camera setting must consume suppressed receipts so re-enabling it cannot replay them.
9. **Instrumentation/cost.** Existing dust has **3 emitters × at most 32 particles**, a **0.12 s** burst interval and **42 m** observer bound. Count emitted/suppressed/coalesced events; capture audio peaks and event prominence separately from physics time. This bounds emitter/particle population, not measured CPU, fill-rate or thermal cost.
10. **Rejecting test.** Existing `godot/tests/footstep_contact_test.gd` rejects support-transport cadence errors; `landing_camera_test.gd:283` checks quiet restart/rewind, native drops and damping; `reclaim_dust_test.gd:86` checks saturation without extra emitters and `110` checks reduced motion. Compare native trajectories with feedback enabled/disabled. Tests were inspected, not executed by this chapter's author.

## K. Recover the complete gameplay checkpoint before considering replay

**Classification: Production-established** checkpoint approach; full binary replay/rollback is **Research-stage or high-risk** for this game's changing topology.

1. **Problem/opportunity.** Player pose alone cannot restore loaded machines or net deformation; replayed walking velocity can falsely launch a rider. Preserve existing machine, carry and topology recovery.
2. **Owner/source.** `capture_machine_checkpoint` (`src/sim/simulation.cpp:7457`) records support/local contact, machine/process state. `restore_from_checkpoint` (`7545`) restores posture, machines, carry and transport. `kit::Kit::restore` (`src/sim/mechanism_kit.cpp:1026`) restores topology/history; `CargoNet::capture/restore` (`src/sim/cargo_net.cpp:205`) records soft-body motion.
3. **Math/units.** Saved contact coordinates are `r_local = T_COM⁻¹ p_world` in metres; after machine restore `p_world = T_COM r_local`. Restart velocity is `v_COM + ω × (p_world−COM)` in m/s, with no replayed relative walking velocity. Snapshot state must include `{pose, velocity, process mass, controls, topology, events}`; pose in m/radians, velocity in m/s/rad/s, fluid/process mass in kg.
4. **Pinned APIs.** `PhysicsSystem::SaveState(StateRecorder&,EStateRecorderState,const StateRecorderFilter*)`/`RestoreState` (`PhysicsSystem.h:165`/`168`) exist, but the main checkpoint uses custom state. Soft-body `SaveState`/`RestoreState` are verified at `SoftBodyMotionProperties.h:129`/`132`; `StateRecorderImpl::Rewind`, `GetData`, `IsFailed` are declared in `StateRecorderImpl.h`. `GetPointVelocity` supplies restored transport.
5. **Native approach.** Extend existing capture/restore when adding persistent mechanics. Restore topology before carry, preserve capsule shape, clear stale contacts and seed presentation epochs quietly. External save files require separate schema/version/error contracts.
6. **Alternatives/tradeoffs.** Whole-system recording may retain more solver state, but still omits non-Jolt energy, process/control and receipt state. Input recording is smaller but requires topology and scheduling reproduction. Networking/rollback has no demonstrated requirement here and would multiply compatibility responsibilities.
7. **Expected behavior.** Restart restores earned machine state, net deformation, inventory and support velocity without walking replay; subsequent contacts earn grounding. These have existing test contracts; replay determinism remains unverified.
8. **Failures/edges.** Destroyed support IDs, disabled saved bodies, carry joints attached before topology restore, incompatible/truncated byte state, unresolved lock failure, stale warm starts, irreversible process expenditure and serialized event replay. Cargo-net serialization assumes a valid live body and internal matching stream; externally corrupted save input is not shown to be supported.
9. **Instrumentation/cost.** Measure snapshot bytes and capture/restore milliseconds with a loaded net and active machines. Record inventory IDs, topology, support-relative velocity and event epoch. Grounded capture frequency can make serialization relevant; actual cost needs profiling before adding compression or whole-world recording.
10. **Rejecting test.** Existing `tests/simulation_tests.cpp:1331` covers death/checkpoint, `1826` covers powered-hold restart and `707` checks current machine inventory. Proposed extension: checkpoint on translating/rotating support with carry, disturb it, restart, assert local contact and transport within declared tolerances, then require real support on the next ticks and zero historical dust/audio bursts. This chapter ran no replay or checkpoint tests.

## L. Detect physics failure and distinguish Android delivery from release readiness

**Classification: Experimental but practical** diagnostic improvement using production-established Jolt error reporting.

1. **Problem/opportunity.** Baseline ordinary physics update discards its result (`src/sim/simulation.cpp:2349`), although Jolt can report ignored contacts when buffers fill. Finite input guards (`8933`, `8757`) do not establish that every post-solve body state is finite. A generated APK alone cannot demonstrate collision reliability or device performance.
2. **Owner/source.** `PhysicsWorld` owns update capacities (`1839`), stepping (`2349`) and published snapshot. `Simulation::advance_frame` validates pacing. `CMakeLists.txt:56` sets warnings-as-errors. `.github/workflows/wo000-delivery-spine.yml:620` cross-compiles native Release; `636` exports the debug Android preset; `godot/export_presets.cfg:22` selects arm64.
3. **Math/units.** Error masks and failure counts are dimensionless; timing is milliseconds. Validate every checked component with `isfinite`, and quaternion norm with `|q·q−1|≤ε` for a declared dimensionless ε. Momentum `m v` (kg·m/s) and energy `½m|v|²` (J) help discriminate an extreme but finite state from NaN. No universal velocity clamp is justified.
4. **Pinned APIs.** `EPhysicsUpdateError` is a bitfield (`Jolt/Physics/EPhysicsUpdateError.h:10`): `ManifoldCacheFull`, `BodyPairCacheFull`, `ContactConstraintsFull` mean some contacts were ignored. `PhysicsSystem::Update` returns it; `GetNumBodies`/`GetNumActiveBodies` (`PhysicsSystem.h:219`/`222`) and `GetBodies` (`235`) support bounded diagnostics. They do not expose a complete commercial-readiness check.
5. **Native approach.** Capture update masks at the solver owner; publish last/cumulative receipts. Check consequential bodies after updates, report failing ID/tick, and reject scenario acceptance on solver errors. Root owns implementation/evidence; this describes the baseline opportunity.
6. **Alternatives/tradeoffs.** Blindly increasing all capacities consumes memory and may hide missing diagnostics. Scanning every static body each tick adds avoidable cost. Start with masks and relevant dynamic-body validation; expand only for a reproduced fault. Do not replace invalid state with fabricated successful support.
7. **Expected behavior.** Routes require zero-error receipts; overload/non-finite states become diagnosable. Package checks identify tested source. No current-source green Android run, phone budget or release APK is claimed.
8. **Failures/edges.** Multiple mask bits, reset losing lifetime evidence, diagnostics racing jobs, a finite but explosive state, high-speed tunneling with no overflow bit, Android-only rounding, export from a red workflow, and stale native libraries. Jolt's MIT SPDX headers are verified; complete distribution licensing still needs the maintained dependency/asset inventory.
9. **Instrumentation/cost.** Record masks, first offending tick/body, body/contact workload and aggregate step timing. Benchmark baseline/candidate on the same route and source configuration. Source identity, native library inclusion, package/signer and checksum checks already exist in CI; on-device p95/p99, sustained memory and thermal measurements remain outstanding.
10. **Rejecting test.** Use a small real Jolt overlap fixture with deliberately insufficient capacities to require nonzero errors, plus an adequately provisioned control. Add an invalid-state case capable of rejecting missing finite checks. Run the ordinary wheel route and retained tests with error masks required zero; keep the existing recovery oracle intact. Android delivery requires the exact-source workflow to succeed; actual device play, pause/resume and frame measurements remain separate acceptance work.
